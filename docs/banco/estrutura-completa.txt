====================================================================================================
1. CONVENÇÕES
====================================================================================================
PK: chave primária. FK: chave estrangeira. UNIQUE: unicidade. CHECK: restrição de expressão.
NOT NULL: obrigatório no banco. NULL: ausência de valor permitida.
1:N: pai com vários filhos. 0..1: associação opcional de no máximo um registro.
Nomes são sensíveis a maiúsculas: em SQL use aspas, por exemplo FROM "User".
String @db.Uuid corresponde a UUID. uuid() é gerado pelo Prisma, sem DEFAULT SQL nas migrations atuais.
@updatedAt é mantido pelo Prisma, não por trigger. Atualizações SQL diretas não o atualizam automaticamente.
DateTime usa timestamp(3) without time zone. A API trabalha com instantes/ISO; o campo não armazena o fuso.
Regras de dia e exibição de jogos usam America/Fortaleza (Patos) na aplicação.
Json corresponde a JSONB. Relações de objeto/lista do Prisma são virtuais, não colunas.
Dinheiro é inteiro em centavos de BRL. Taxas Bps: 10.000 = 100%; 1.000 = 10%; 200 = 2%.
UNIQUE nullable permite vários NULLs no PostgreSQL utilizado.
CASCADE apaga filhos com o pai. RESTRICT impede exclusão de pai referenciado. SET NULL limpa o vínculo opcional.
NO ACTION mantém a conferência de integridade do banco conforme a constraint.
Permissões HTTP e regras compostas da API não são garantias automáticas de SQL.

====================================================================================================
2. TABELAS POR MÓDULO
====================================================================================================

Identidade e acesso:
  User: Contas de torcedores, administradores e funcionários. Perfil, permissões e saldo de pontos.
  Session: Sessão autenticada, hash do segredo atual de refresh, validade absoluta e revogação.
  RefreshToken: Histórico de renovação de sessão, com consumo único e detecção de reutilização.

Associação:
  Plan: Plano de sócio, preço de mensalidade e desconto em ingresso.
  Membership: Matrícula de uma conta em um plano, com estado e validade.

Jogos e ingressos:
  Match: Partida, publicação e janelas de venda e portaria.
  Sector: Setor de uma partida, preço, capacidade total e habilitação de venda.
  Ticket: Pedido por conta/partida; um registro representa de uma a quatro pessoas.
  TicketPayment: Conferência do recebimento externo pelo administrador ou registro da gratuidade.

Portaria:
  TicketAdmission: Entrada confirmada: quantidade, operador, leitura e chave de idempotência.
  TicketAccessCode: Hash do código digitável temporário, compartilhando leitura/versão/vencimento com o QR.
  GateAssignment: Escala que libera uma conta de funcionário para operar um setor de uma partida.

Auditoria:
  AuditLog: Histórico de ações relevantes com ator, ação, entidade e detalhes JSON.

Relacionamento:
  Partner: Parceiros e benefícios exibidos ao torcedor; vínculo financeiro com Merchant é opcional.
  Prediction: Palpite de placar por conta/partida; apuração e premiação ainda pendentes.
  Referral: Indicação de amigo, negócio ou parceiro; não envia mensagem automaticamente.

Pontos e experiências:
  PointEntry: Extrato de créditos e débitos de pontos, separado do saldo monetário.
  Reward: Experiência trocável por pontos, com custo, estoque e habilitação.
  Redemption: Resgate de uma experiência pela conta, com custo histórico em pontos.

Cashback e split:
  Tenant: Instituição/marca no módulo financeiro; não implica multi-tenant completo do produto.
  Merchant: Estabelecimento compartilhável entre instituições, com ofertas e operadores.
  MerchantOffer: Condições de cashback/comissão entre instituição e estabelecimento.
  MerchantOperator: Permissão de uma conta para operar o caixa de um estabelecimento. Não é role GATE.
  CashWallet: Carteira monetária por instituição/conta, com saldo líquido em centavos.
  PaymentCharge: Venda/cobrança com split, beneficiário, estado e idempotência. Não é TicketPayment.
  CashEntry: Lançamento de crédito ou compensação de cashback vinculado à venda e carteira.
  PaymentEvent: Evento normalizado de liquidação/estorno, com ID externo e fingerprint de consistência.

Infraestrutura:
  _prisma_migrations: Controle técnico de migrations. Não é model de negócio da aplicação.

3. ENUMS PERSISTIDOS
====================================================================================================
CashEntryKind: CASHBACK | REVERSAL
MembershipStatus: PENDING | ACTIVE | EXPIRED
PaymentChannel: CASHIER_QR | CUSTOMER_QR
PaymentStatus: PENDING | PAID | REFUNDED | CANCELED
ReferralKind: FRIEND | BUSINESS | PARTNER
TicketPaymentMethod: MANUAL | FREE
TicketStatus: PENDING | ISSUED | USED | CANCELED
UserRole: USER | ADMIN | GATE

EXPIRED não existe no enum TicketStatus: é calculado pela API quando a reserva vence.
Referral.status e AuditLog.action são strings. PaymentEvent.type também é string, com CHECK SQL próprio.

====================================================================================================
4. RELAÇÕES E CARDINALIDADES
====================================================================================================

N:N explícitas: User <-> Sector via GateAssignment; User <-> Merchant via MerchantOperator;
Tenant <-> Merchant via MerchantOffer; User <-> Reward via Redemption (um resgate por par).
Vínculos lógicos: AuditLog.entityId é polimórfico, sem FK; scanId associa emissão/entrada na API sem FK entre TicketAccessCode e TicketAdmission.
As FKs independentes de Ticket não garantem que o setor pertença à partida; a API garante essa correspondência.

    CHECK ("entryVersion" >= 0)
  Ticket_price_nonnegative [CHECK]
    CHECK ("priceCents" >= 0)
  Ticket_quantity_range [CHECK]
    CHECK (quantity >= 1 AND quantity <= 4)
  Ticket_used_quantity_valid [CHECK]
    CHECK ("usedQuantity" >= 0 AND "usedQuantity" <= quantity)
  Ticket_voided_quantity_valid [CHECK]
    CHECK ("voidedQuantity" >= 0 AND "voidedQuantity" <= (quantity - "usedQuantity"))
  Ticket_matchId_fkey [FOREIGN KEY]
    FOREIGN KEY ("matchId") REFERENCES "Match"(id) ON UPDATE CASCADE ON DELETE RESTRICT
    ON DELETE RESTRICT; ON UPDATE CASCADE
  Ticket_sectorId_fkey [FOREIGN KEY]

    CREATE INDEX "Ticket_userId_matchId_idx" ON public."Ticket" USING btree ("userId", "matchId")

OBSERVAÇÕES:
  - O índice UNIQUE parcial Ticket_userId_matchId_active_key garante uma venda ativa por conta/partida somente quando deletedAt IS NULL. Excluídas podem coexistir com uma nova compra. O índice parcial é mantido pelo SQL da migration, fora do @@index não único do Prisma.
  - Exclusão lógica invalida acesso e mantém pagamentos e entradas. Somente quantidade não utilizada é liberada no estoque. Edição paga preserva o valor recebido; após entrada o setor não pode mudar nem a quantidade diminuir abaixo do uso.
  - As FKs não garantem que setor e pedido sejam da mesma partida; essa conferência é feita pela API.
  - Não há assento numerado: o controle é por setor/quantidade.

8. REGRAS DA API E LIMITES DO MODELO
====================================================================================================
AUTENTICAÇÃO: login único; cadastro público USER; ADMIN cadastra GATE. JWT de acesso padrão de 15min; refresh rotativo com validade absoluta padrão de sete dias. Role/active/sessão são conferidos na API.
ASSOCIAÇÃO: desconto só com ACTIVE e validade futura. A API pode apresentar associação vencida como EXPIRED sem atualizar fisicamente o enum.
COMPRA: revisão de até 60s sem reserva de estoque. Não há tabela de quote. Reserva paga dura até 15min, limitada à janela de vendas/início da partida. Gratuitos são emitidos com TicketPayment FREE.
PREÇO: unitário com desconto é arredondado por pessoa e multiplicado pela quantidade. expectedTotalCents compara o preço revisado; não é coluna nem fonte de preço.
ESTOQUE: soma ingressos ISSUED/USED e reservas PENDING válidas. Setor e partida precisam corresponder. Não existe escolha de assento numerado.
CONCORRÊNCIA: operações críticas usam transação Serializable com até três tentativas para conflito P2034. Constraints isoladas não substituem a transação.
PAGAMENTO DE INGRESSO: recebimento manual exige reserva válida, valor exato e referência única. Não há cobrança bancária automática ou reembolso de ingresso pago implementados.
PORTARIA: emissão/pagamento corretos, titular ativo, janela/partida/setor, quantidade restante e escala são conferidos no servidor. QR e código compartilham leitura/versão e vencimento de até 45s.
CONSUMO: entrada incrementa entryVersion, grava quantidade, protocolo e auditoria na mesma transação. Repetição válida retorna ALREADY_RECORDED; consulta não autoriza nem consome. Não há liberação offline.
ESCALA: GateAssignment.userId não é restringido a GATE por SQL. Cadastro e autorização são regras da API, revalidadas dentro da transação de entrada.
PONTOS: check-in rende 30 por dia em America/Fortaleza, identificado por sourceKey. Resgate debita pontos/estoque e grava extrato na mesma transação. Não há trigger de reconciliação automática para SQL arbitrário.
PALPITES: envio antes do jogo; apuração e premiação ainda pendentes. Indicações são persistidas sem envio automático de mensagens.
CASHBACK: carteiras por tenant/conta, separadas dos pontos. Modelo B cria venda no caixa; modelo A usa QR fixo condicionado à oferta. Não há gateway real configurado, gasto de saldo ou devolução parcial implementados.
SPLIT: valores da venda são históricos. Evento confirmado precisa corresponder a valor/split/moeda/validade. Duplicidade é controlada por ID externo/fingerprint e lançamentos únicos.
ESTORNO: crédito/compensação registrados uma vez; pagamento tardio não recria saldo após estorno. Extrato usa adição na API, sem trigger SQL de imutabilidade.
WHITE-LABEL: Tenant isola o cashback. Identidade, planos, jogos e portaria ainda não têm isolamento completo por clube.
SEM TABELAS ESPECÍFICAS: assentos numerados, push, pedidos da boutique, recuperação de senha, MFA, matrícula da escolinha e checkout de quote não são módulos persistidos implementados.
SEM TRIGGERS/PROCEDURES DE NEGÓCIO declaradas pelas migrations; regras compostas ficam nos services/models.
CAMPOS CALCULADOS/DE RESPOSTA: available, remainingQuantity, entryQr, availableCents, debtCents e serverTime não são colunas destas tabelas.

10. ARQUIVOS E MANUTENÇÃO
====================================================================================================
Schema: apps/api/prisma/schema.prisma
Migrations: apps/api/prisma/migrations/
Configuração Prisma: apps/api/prisma.config.ts
Conexão: apps/api/src/config/database.js
Ambiente: apps/api/src/config/env.js e .env locais (segredos não incluídos neste documento)
Bootstrap: apps/api/prisma/bootstrap.js | seed opcional: apps/api/prisma/seed.js
Consultas/transações: apps/api/src/models/ | serviços: apps/api/src/services/ | regras: apps/api/src/lib/
Contratos de resposta: packages/shared/types.ts | Docker PostgreSQL: docker-compose.yml

Comandos executados somente quando o responsável os invoca:
  npm run db:prepare -> generate, migrate deploy e bootstrap administrativo.
  npm run db:migrate -> desenvolver migrations; npm run db:deploy -> aplicar migrations existentes.
  npm run db:studio -> abrir ferramenta interativa de dados.
  npm run auth:cleanup --workspace @nacional/api -> limpar sessões vencidas e códigos expirados.

Ao mudar schema/migrations, atualizar este TXT. Nenhum registro de usuário ou credencial foi exportado.
